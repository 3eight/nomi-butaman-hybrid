# 能美豚饅 蒸し・会計・注文管理システム（仕様書 v0.2 準拠）

## 1. 概要・目的
イベント出店における「能美豚饅」の調理（蒸し・揚げ）、注文受付、会計記録、受け渡し、せいろ段別在庫推計、および精算集計を一元管理するシステム。
- **対象環境**: イベント出店現場（複数スマートフォンでの同一出店データ共有を想定）
- **目標マイルストーン**: 2026年11月1日
- **Google Drive 正本参照**:
  - 索引: `https://docs.google.com/document/d/1VUVEiI1KIX4FiESLiTMNHj4ne7fM78CSVp8Di0h0pRI/edit`
  - 詳細仕様 (2026-10-15 18時台 改訂 v0.2): `https://docs.google.com/document/d/12kK-osCjoeoiWtSXdLC6vX4i2SyYY1HP1BFh4O6qIlw/edit`
- **現在フェーズのスコープ**:
  - 画面案（ワイヤーフレーム風・近未来UI）の提示は保留し、**仕様保存・データモデル・業務ロジックの実装および自動テスト**を先行する。
  - 公開デプロイ・有料サービス契約・外部送金は行わない。

## 2. 商品・イベント設定仕様

### 2.1 取扱商品と調理方法
- イベントごとに取扱商品を切り替え可能とする（例: 豚まん、あんバタまん、ポテト等）。
- 商品カテゴリ:
  - `MAN`（まん類: 5個ごと無料サービスの集計対象）
  - `SIDE`（サイドメニュー: ポテト等、無料サービスの集計・選択対象外）
- 調理方法 (`CookingMethod`):
  - `STEAM`（蒸し）
  - `FRY`（揚げ）
- 同一商品でも「商品 × 調理方法（蒸し/揚げ）」の単位（SKU相当）で注文・在庫・提供を管理する。

### 2.2 5個ごと1個無料サービス（本部負担）
- **算出基準**:
  - 1注文内の**有料まん類 (`MAN`) の合計数量** 5個ごとに、1個を無料サービス枠として付与する。
  - 計算式: `付与可能無料数 = floor(有料まん類合計数 / 5)`
  - 無料サービス分そのものは「5個ごと」の母数（有料数）に含めない。
  - ポテト等の非まん類 (`SIDE`) は母数にも無料対象にも含めない。
- **無料品の内訳選択**:
  - 無料サービス品も、顧客が「まんの種類（豚まん/あんバタまん等）× 調理方法（蒸し/揚げ）」を自由に選択できる。
- **イベント単位ON/OFF・注文単位の辞退**:
  - イベント設定で無料サービス制度自体の `ON / OFF` を切り替え可能とする。
  - イベント設定が `ON` の場合でも、**注文単位で無料サービスの全部または一部を辞退（受け取らない）可能**とする。
  - **重要ルール**: 辞退された無料枠分は、**物理在庫の引き当て・減算を行わず、本部負担のサービス費用にも一切計上しない**（実態として提供された無料個数のみを在庫減算・本部負担計上する）。

### 2.3 収益配分・価格・原価・廃棄・経費
- **価格・配分設定（設定可能・未確認フラグ管理）**:
  - ポテト配分: 本部 50% / 出店者 50%（原価は `未精査 / unverified` として保持）。
  - 豚まん: 500円 / 本部50%・出店者50% は過去条件のため**再確認が必要 (`unverified: true`)** として保持し、イベント設定で変更可能とする。
- **廃棄（ロス）管理**:
  - 廃棄は以下の2区分を明確に分離して記録・集計する:
    1. `DEFECT_HQ`（商品不良 = 本部負担、出店者ペナルティ0円）
    2. `NEGLIGENCE_VENDOR`（蒸しすぎ等の過失 = 出店者負担 **250円/個**）
- **経費管理**:
  - 経費は任意入力とする。
  - **未入力（`null` / 未登録）の状態を「0円確定」として扱わない**（`UNENTERED` と `CONFIRMED`（0円確定含む）を明確に区別する）。

## 3. 注文・会計・受け渡し仕様

### 3.1 注文構成とステータスの独立管理
- **注文の構成要素**:
  - 注文番号 (`orderNumber`)
  - 有料明細（商品 × 蒸し/揚げ × 数量 × 単価）
  - 無料サービス内訳（商品 × 蒸し/揚げ × 数量）、辞退数 (`declinedFreeCount`)
  - 客の特徴タグ（任意・数タップで選択できる複数タグ案。**入力必須にはしない**）
  - 変更履歴 (`history`)
- **支払状態と受渡状態の分離**:
  - 先払い標準だが、後払いも許容するため、支払状態 (`PaymentStatus`) と受渡状態 (`FulfillmentStatus`) は完全に独立させる。
  - 支払手段: `CASH`（現金）、`PAYPAY`（PayPay）、`TOCHITSUKA`（トチツーカ）の記録のみ（決済代行・外部通信は行わない）。

### 3.2 注文数量変更・差額徴収・返金待ち・案内表示との区別
- 同一注文に対する後から数量変更（追加・削減・無料内訳変更・辞退変更）に対応する。
- 注文変更により注文合計金額 (`totalAmount`) と既収金額 (`paidAmount - refundedAmount`) に差が生じた場合:
  - `netPaid < totalAmount` → **`ADDITIONAL_COLLECTION_PENDING`（差額徴収待ち）**
  - `netPaid > totalAmount` → **`REFUND_PENDING`（返金待ち）**
  - `netPaid == totalAmount && totalAmount > 0` → **`PAID`（支払完了）**
- **重要ルール（案内表示と完了の分離）**:
  - 画面やロジックが「〇〇円いただきます」「〇〇円お返しします」と**案内表示（計算提示）しただけでは、入金完了・返金完了にしない**。
  - 必ずスタッフによる明示的な「入金記録アクション (`recordPayment`)」または「返金記録アクション (`recordRefund`)」を経て初めて完了ステータスへ遷移する。

## 4. せいろ（蒸し器）・調理バッチ・在庫仕様

### 4.1 せいろ構成と段番号
- **標準構成例**:
  - 通常せいろ: 5個 × 4段 × 2セット（計8段）
  - 電気せいろ: 6個 × 4段（計4段、※容量は現場未確認フラグ `capacityVerified: false` として保持し設定変更可能とする）
- **段の固定番号**:
  - 実物のせいろ1段ごとに付与した固定番号（例: 1〜4, 5〜8, 9〜12 ※番号体系は案であり設定変更可能）と、画面上の段タイマー表示を1対1で一致させる。
- **蒸し時間**:
  - 標準約40分（設定変更可能、デフォルト40分）。
- **揚げ工程**:
  - 現時点では詳細運用が `未確認 (unverified)` のため、商品×揚げの注文・在庫記録は可能としつつ、工程仕様は未確認項目として分離管理する。

### 4.2 途中追加（バッチ・スロット独立タイマー）と満了後の扱い
- **途中追加への対応**:
  - ピーク時に「既存の段の空き位置へ1個だけ途中で冷凍品を追加する」運用が発生する。
  - そのため、段全体で1つのタイマーにするのではなく、**段内の位置（スロット）または投入バッチ (`SteamingBatch`) 単位で独立したタイマー（投入時刻・蒸し上がり予定時刻・調理確認状態）**を保持する。
- **蒸し上がり後の保持と調理確認状態の分離**:
  - 蒸し上がり後も商品はせいろの中に置いたまま保温・待機される。
  - **タイマー満了（予定時刻到来）によって自動的に段を空にしたり、無条件に提供可能と確定したりしない**。
  - 各バッチは以下の状態を明確に区別する:
    1. `STEAMING`（蒸し中：予定時刻前、または予定時刻経過後まだ調理確認していない状態 ※予定時刻到来フラグ `isTimerExpired` は時刻比較で算出）
    2. `CONFIRMED_READY`（調理確認済み：スタッフが蒸し上がりを実際に確認し、引渡し可能になった状態）

## 5. 予約・引当・受渡減算・段別取り出し訂正（暫定了承フロー）

### 5.1 6つの概念の分離と二重割当・二重減算防止
システムは以下の状態を厳密に分離して管理する:
1. **予約 (`RESERVED`)**: 注文受付時に未渡しの必要個数として確保された枠（注文単位の未引渡必要数およびバッチへの仮割当）。
2. **蒸し中 (`STEAMING`)**: せいろに投入され調理中のバッチ。
3. **調理確認済み (`CONFIRMED_READY`)**: 蒸し上がりが確認され、せいろ内で取り出し可能な物理在庫。
4. **せいろ内物理在庫 (`remainingQty`)**: 現在せいろの各段に残っている推計個数。
5. **支払状態 (`PaymentStatus`)**: 未払い / 支払済 / 差額徴収待ち / 返金待ち。
6. **引渡し状態 (`FulfillmentStatus`)**: 待機中 (`WAITING`) / 一部引渡 (`PARTIAL`) / お渡し完了 (`DELIVERED`) / キャンセル (`CANCELLED`)。

- **二重割当・二重減算の防止**:
  - 複数注文が同時に待機している場合、各注文の引当（または取り出し元案内）はバッチの利用可能残数 (`availableForAllocation = remainingQty - reservedByOtherOrders`) を超えて重複割当しない。
  - 注文の「お渡し完了 (`completeOrderDelivery`)」実行時は、冪等性チェック（すでに引渡し完了している注文・明細の二重実行防止）を行い、二重減算を防止する。

### 5.2 取り出し元段の自動案内と「お渡し完了」による自動減算
- **通常フロー（段別入力不要）**:
  - システムが調理確認済み (`CONFIRMED_READY`) の古いバッチ（FIFO）等から、**「どの段（および位置/バッチ）から何個取り出すか」を自動案内 (`PickSuggestion`)** する。
  - スタッフが注文の **「お渡し完了」ボタンを押すだけで、案内された段（バッチ）から自動的に個数を減算**する。通常時はスタッフが段番号を手入力する必要はない。
- **最少訂正フロー（違う段から取った場合の付け替え）**:
  - 現場で案内とは違う段から取り出してしまった場合のみ、**直前注文の1個（または指定個数）を「案内された元の段」から「実際に取った段」へ付け替える最少訂正 (`correctTierPick`)** を行える。
  - 訂正時は、元の段の残数を戻し、実際の段の残数を減算し、**訂正履歴 (`TierCorrectionRecord`)** を記録する。
- **推計在庫の免責・前提明示**:
  - 段別残数は「システムの指示に従う（または訂正入力を行う）前提の推計値 (`isEstimated: true`)」であり、未申告の取り違えをセンサー等で自動実測できるとは称さない。

## 6. 予測・助言とマルチスマホ同期（未検証項目の明示）

### 6.1 追加蒸し・少量・停止の助言
- 補充判断の助言（`ADD_MORE` / `SMALL_BATCH` / `STOP`）において、以下の2つを混同せず分離して出力する:
  - **実績値 (`actuals`)**: 現在の確定待ち注文数、調理確認済み残数、蒸し中残数、累計販売実績。
  - **予測値 (`forecast`)**: 時間帯・直近ペース等から推計した今後の予測需要。

### 6.2 同期・通信切断・バックグラウンド通知（未検証扱い）
- 複数スマホで同じ出店データを共有する構成を想定し、状態のスナップショット入出力・イベントログ構造を備えるが、**リアルタイム同期方式・通信切断時の競合解決・画面非表示中（バックグラウンド）の通知挙動は「未検証 (`UNVERIFIED`)」**として扱い、検証済みと偽らない。

## 7. 受入条件（Acceptance Criteria）一覧

| ID | カテゴリ | 受入条件 | テスト検証対象 |
|---|---|---|---|
| AC-01 | サービス計算 | 有料まん類合計5個ごとに1個無料枠が付与されること（4個→0、5個→1、9個→1、10個→2）。ポテト等の非まん類や無料分自体は母数に含まないこと。 | `service_calculation` |
| AC-02 | 無料内訳・辞退 | 無料分も「まんの種類×蒸し/揚げ」を選択できること。イベント単位ON/OFFが機能し、ONでも注文単位で辞退（全部/一部）でき、辞退分は在庫減算・本部負担サービス費用に計上されないこと。 | `service_decline` |
| AC-03 | 注文変更・差額/返金 | 同一注文の数量変更時、差額徴収待ち・返金待ちが正しく算出され、変更履歴が残ること。**案内表示（計算結果の取得）だけでは入金完了・返金完了にならず**、明示的な記録操作でのみ完了になること。 | `order_modification_and_payment` |
| AC-04 | 予約・受渡・二重防止 | 支払状態と受渡状態が独立して遷移すること。複数注文間で同一在庫が二重割当されず、「お渡し完了」で案内された段から減算され、二重減算が起きないこと。 | `reservation_and_delivery` |
| AC-05 | 段別取り出し訂正 | 通常は「お渡し完了」のみで段減算され、違う段から取った場合のみ、直前注文の1個等を実際の段へ付け替える最少訂正ができ、両段の推計残数と訂正履歴が正しく更新されること。 | `tier_pick_correction` |
| AC-06 | 途中追加・満了保持 | せいろ段内に後から1個だけ冷凍品を途中追加した際、既存分と独立したタイマー（予定時刻・調理確認状態）を持つこと。タイマー満了時刻を過ぎても自動で段が空にならず、調理確認状態と予定時刻が区別されること。 | `mid_stream_addition_and_timer` |
| AC-07 | 廃棄・経費・精算 | 廃棄が「商品不良＝本部負担」と「蒸しすぎ等過失＝出店者250円/個」に分離集計されること。経費未入力が0円確定として扱われないこと。予測と実績が分離されていること。 | `waste_expense_and_settlement` |
